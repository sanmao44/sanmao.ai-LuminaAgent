# 沧元视频接入排查记录

核对日期：2026-11-23。范围为视频任务提交、查询、恢复及主界面/超级画布的模型参数；不改变 Provider、Task 或 Canvas 的 authoritative owner。

## 故障链与修复边界

本轮确认了几条会造成“服务商已生成，前端却失败”或重复提交的代码路径：

| 问题 | 修复后的行为 |
| --- | --- |
| 旧模型发现把官方连接存为 `openai-videos`，提交丢失专用首帧/参考图字段 | 官方连接读取时归一化为 `cangyuan-videos`，按模型文档发送 `first_image_url`、`reference_image_urls` 等字段；新发现结果也保存正确协议 |
| 旧连接继承 `/v1/tasks/{id}` 查询模板 | 官方视频任务使用 `GET /v1/videos/{task_id}`；修复继承的通用模板，保留真实自定义路径 |
| 提交尚未返回任务 ID 时，刷新/恢复路径可能再次提交 | Repository 提交占用覆盖首次 POST；已经开始但结果不确定的提交不自动重发。JSON fallback 的读—改—写使用跨实例/进程文件锁 |
| 同一原任务被并发手动重试，或从旧原任务绕过受理不明的子重试 | 手动重试复用原子占用和稳定轮次键；复用正在运行的子任务，阻止受理不明的任务重发。完成后用户仍可明确发起下一轮生成 |
| 已有服务商任务 ID，但本地查询失败后从生成入口重试 | 沿原服务商任务 ID 查询/恢复；查询失败与服务商明确生成失败分开处理 |
| POST 超时、连接中断、响应读取/解析失败或成功响应缺任务 ID | 标记“可能已受理”，阻止自动再 POST；明确拒绝与受理结果不确定分别处理 |

目标是一条用户生成意图只触发一次上游提交。服务商响应丢失且没有可查询任务 ID 时，客户端无法证明上游未受理；此时显示结果待确认，不能通过盲目重发保证“成功”。已有的两条上游任务应查询并恢复，不能为修复前端再创建第三条。

完成结果按官方响应的 `video_url` 或 `data[0].url` 读取，保留服务商 URL；不拼接 `/content`。排队响应回显的参考素材不能当成生成结果。轮询保持官方建议的 5–10 秒间隔及至少 30 分钟的等待窗口。直接 `wan3.0-video` 和官方 `doubao-seedance-*` 返回链接可能要求下载；浏览器不支持直接预览不等于生成失败。

## 模型与参数覆盖

本轮重新获取官方 manifest 中的 **146 个视频模型**并与本地生成目录逐项比对：138 个有参数说明；8 个参数说明为空，继续禁用提交，避免猜测接口。目录无缺失或过期模型；本轮新增 `gemini-omni-1.2-flash`，它和 `gf1-gemini-omni-1.2-flash` 的参数不能混用。

参数说明为空的模型：

- `kl3-kling-2.1`
- `kl3-kling-2.6`
- `kl3-kling-2.6-motion`
- `kl3-kling-3.0`
- `kl3-kling-4.0`
- `kl3-kling-4.0-flash`
- `sd15-seedance-2.0-2`
- `sd16-seedance-2.5-2`

参数处理原则：

- 明确枚举按枚举校验；分辨率大小写归一为官方值。推荐列表保持开放，不冒充完整允许列表。
- 同时阅读参数表、模型介绍、警告和说明文字。Vidu 等正文要求参考素材的模型，不能因为 JSON 的 `required` 缺失就放行纯文本提交。
- 明确禁止的组合在提交前拦截，包括 `kling-o3` / `sd11-seedance-2.0` 的 4K 限制，以及 `sd10-seedance-2.5` 的 720P 时长限制。UI 提示与实际提交校验共用模型能力。
- Wan6 正文出现“当 resolution=1080P 时，resolution 不支持 1080P”的自相矛盾描述。保留官方说明，不据此推断禁止项；该组合仍需服务商澄清。
- 首帧、尾帧、参考图、参考视频、音频开关、随机种子及高级参数仅在对应模型支持时展示/提交。主界面与超级画布使用同一能力来源；切换模型时清除不兼容输入。

## 验证证据与限制

`tests/cangyuan-video-capabilities.test.mjs` 遍历 146 个目录项：为 138 个有文档模型构造最小有效输入，验证字段是否声明、类型、枚举、范围、必填项及插入默认值后的组合；验证其余 8 个不可提交。这是**模拟参数/序列化矩阵，不是 138 个模型的真实付费生成**。

其余行为覆盖分别位于：

- `tests/video-providers.test.mjs`：旧协议映射、专用字段、任务查询地址、结果解析、POST 受理不确定性。
- `tests/video-task-service-retry.test.mjs`、`tests/video-task-submission-claim.test.mjs`：单次提交、并发占用、查询恢复和重试边界。
- `tests/task-store-concurrency.test.mjs`：独立实例/子进程串行修改、死进程锁恢复、活跃锁保护及失败清理。
- `tests/canvas-api.test.mjs`、`tests/canvas-video-editor-behavior.test.mjs`、`tests/video-studio-model-controls.test.mjs`：两处创作入口的参数落地与模型切换。

这些自动化检查不能证明所有服务商线路实时可用，也不能代替逐个模型的真实生成。生产任务恢复、全量检查、构建及同步结果应以本次交付日志为准，不从目录数量推导。

### 已有真实任务恢复

2026-11-23 使用更新后的本地服务，仅沿原服务商任务编号查询，已恢复此前 `gf1-gemini-omni-1.2-flash` 的失败记录：任务状态为完成，得到 1 条远端视频及 1 份本地保存结果，原任务编号保持不变；创作日志同步恢复为成功。恢复期间没有重新提交生成请求。另一个旧编号曾被上游返回 `task_not_exist`，不能据此再次自动生成。

### 界面调整

主视频工作台的模型参数始终展开，移除参数区域的内层限高与嵌套滚动，保留外层正常滚动。基础控件按可用宽度排列为两列或三列，提示词保持紧凑并支持放大编辑。长时长模型使用预设时长与自定义秒数，不生成数百个下拉选项。主界面与超级画布均有全目录控件渲染测试；这些测试不能代替实际浏览器布局验收。

浏览器逐项切换 146 个画布目录项后，发现 26 个型号的随机种子输入存在固有宽度溢出，已复用项目输入样式并限制网格轨道。Muse 导演等多文本模型原先三列布局留下空位，现按参数面板实际宽度启用四列，让两个长文本框并排；外框宽度、节点位置与参数/注释完整性保持不变。

### 本轮最终验证

- `npm run check`：3,487 项通过，1 项跳过，0 失败；类型检查、更新清单检查、架构约束及生产构建均通过。隔离构建产生的临时类型路径恢复后再次运行类型检查通过。
- 在隔离浏览器数据中逐项切换主界面的 138 个可用型号、画布的全部 146 个目录项；生成请求被拦截，没有为布局验收付费生成。最终未检测到控件越出自身标签宽度、原生下拉框或折叠的生成参数。空规格的 8 个型号仍不可提交。
- 画布外框保持 760px；参数最多的 Muse 导演仍需纵向平移查看，全部参数和说明保留，编辑器继续在节点下方。布局量测不能证明每种窗口尺寸及所有内容长度均已穷尽。
